# Lecture 11.01 — Static vs. Dynamic Analysis

## Why this matters

Stage 7 (Assembly) taught you to read instructions; Stage 6/8 taught you
the ELF/PE formats those instructions live inside. This stage is where
those merge into an actual skill: understanding a binary you don't have
source for. Everything here is a hard prerequisite for Stage 12 — you
cannot triage malware you can't disassemble, and you cannot tell whether
a sample is doing something interesting without knowing whether to trust
what a disassembler tells you or what actually happens when it runs.
That tension — read vs. run — is the entire subject of this lecture.

## Core concepts

**A disassembler is guessing, not reading, and on x86 that guess can be
wrong.** x86 is a variable-length instruction set — instructions are
anywhere from 1 to 15 bytes, and nothing in the file format marks where
one instruction ends and the next begins. A disassembler recovers this
by *assuming* a starting point (function entry, `.text` start) and
decoding forward, or by following control flow recursively from known
entry points. If code and data are interleaved, or a jump lands one
byte off from where the disassembler assumed an instruction started, the
decode can desync — every subsequent "instruction" is misread, because
it's really the tail end of a previous one plus the start of the next,
reinterpreted as something that was never actually executed. Ghidra's
decompiler adds a further layer on top of this: its pseudo-C output is
a *hypothesis* about what source produced this disassembly, generated by
pattern-matching decoded instructions against known idioms — genuinely
useful, but a step removed from ground truth, not identical to it.

**Running the binary sidesteps the guessing entirely, because the CPU
doesn't guess.** The processor executes whatever bytes are at the
instruction pointer, unambiguously, every time. Dynamic analysis (gdb,
single-stepping, watching registers and memory as the binary actually
runs) gives you ground truth about what happened on *this* execution,
with *this* input — at the cost of only showing you one path through
the program. A branch not taken this run stays invisible no matter how
long you watch.

**This is the actual trade-off, not a matter of taste: static analysis
gives you the map, dynamic analysis gives you the territory.** Static
analysis (in principle) covers every path the binary could take, at the
cost of being an interpretation that can be wrong. Dynamic analysis is
never wrong about what it shows you, at the cost of showing you only
what one run actually did. Real RE work interleaves both: read
statically to form a hypothesis about what a comparison or function is
doing, then confirm dynamically by breakpointing there and inspecting
the real values — each method covers the other's blind spot.

**Packed and self-modifying binaries are where static-only analysis
fails outright, not just imprecisely.** A packer stores the real
payload compressed or encrypted inside the file and unpacks it into
memory at runtime, before jumping to it. Ghidra can show you the
unpacking stub — that code genuinely exists in the file — but it cannot
show you what that stub *produces*, because those bytes don't exist as
disassemblable instructions until the stub has already run. Static
analysis of a packed sample often looks nearly empty (few strings, one
suspicious high-entropy blob, a tiny import table) precisely because the
interesting code isn't there yet.

**Anti-debugging techniques are a direct, deliberate countermeasure
against dynamic analysis specifically — not analysis in general.**
`ptrace`-based self-detection (a process can only be `ptrace`d by one
debugger at a time, so a binary that tries to self-attach and fails
knows something else is already attached), timing checks (single-
stepping is orders of magnitude slower than free execution, so measuring
elapsed cycles — e.g. with `rdtsc` — around a sensitive section detects
that it's being stepped through), and checking debug registers or
process flags all exist because static analysis alone can't trigger
these checks — they only fire when the binary is actually being run
under observation. This is exactly the skill 11.1 requires you to
demonstrate: identifying the check, then working around it (patch it
out, or defeat the specific mechanism it relies on) rather than
retreating to pure static analysis and hoping.

## Check yourself

1. Why can a disassembler misinterpret a jump target that lands one
   byte into what was meant to be a different instruction, and what does
   the resulting "desync" look like in the listing that follows?
2. In what specific sense is Ghidra's decompiled pseudo-C a *hypothesis*
   about the binary rather than a fact about it?
3. Give a concrete reason a packed binary can look almost empty under
   static analysis in Ghidra yet do a lot once actually run.
4. A crackme measures elapsed cycles around a comparison and aborts if
   the gap is too large. Why does single-stepping through that
   comparison specifically trip this check, when running the binary
   freely wouldn't?
5. You've located the exact comparison instruction in Ghidra but the
   value it compares against is computed at runtime, not a literal in
   the file. What does breakpointing there in gdb get you that reading
   the disassembly alone can't?
